# Backpack 매도 RFQ 잔고 조건 추가 조사

조사일: 2026-09-13. 기존 실험 기록과 공개 자료를 대조했습니다. 새 거래는 실행하지 않았습니다.

## 답할 수 있는 범위

계정 자산 부족 시 거래를 진행하지 않을 수 있다는 정책은 약관에서 확인했습니다. 주식 보유분을 계정에 기록하는 방식도 설명되어 있습니다. 그러나 **이용자가 견적을 수락하기 전, RFQ 제출 단계부터 잔고를 검사하는 이유와 검사 주체는 공개 자료에서 확인하지 못했습니다.**

따라서 다음 세 가지를 나눠야 합니다.

- 관측: 수락을 기다리는 방식의 매도 RFQ 제출이 잔고 부족으로 거절됐습니다.
- 공식 설명: 계정 자산 부족 시 거래를 진행하지 않을 수 있으며, 이용자의 주식 보유분은 내부 장부에 기록됩니다.
- 해석: 이번 경로는 거래 가능한 자산을 미리 확인하는 것으로 보입니다. 다만 검사 시점을 정한 설계 이유나 연결 증권사의 요구인지는 미확인입니다.

## 2. 일반 토큰 교환에도 RFQ와 사용 가능 잔고 조건이 있습니다

[Backpack Convert 안내](https://support.backpack.exchange/exchange/trading/convert)는 일반 토큰 교환에도 RFQ를 사용한다고 설명합니다. 또한 Convert에서는 차입을 지원하지 않으며, 다른 포지션이나 차입의 담보로 묶인 토큰은 교환할 수 없다고 안내합니다.

이는 **RFQ와 잔고 제한의 결합 자체를 RWA 고유의 특징으로 볼 수 없다는 근거**입니다. 다만 Convert도 동일하게 RFQ 제출 단계에서 같은 오류를 내는지는 이 문서만으로 확인되지 않습니다. Convert의 견적 유효시간이나 차입 제한을 주식 RFQ에 그대로 적용해서도 안 됩니다.

## 3. 연결 기관의 자료는 역할 분담을 보여 주지만 오류의 출처를 확정하지 못합니다

[Atomic Vaults의 거래소 연동 안내](https://docs.atomicvaults.com/guide/cex/)는 거래소 대표 계정 아래 이용자별 계정을 두는 구조와 거래 전 잔고·담보 확인 절차를 설명합니다. [위험 한도 안내](https://docs.atomicvaults.com/guide/us/risk-limits/)에는 거래 상대 사업자별 주문 한도가 있으며, 실제 운영 환경의 상세 조건은 도입 과정에서 제공한다고 적혀 있습니다.

이 자료는 거래소 화면 뒤에서 계정 관리와 주문 검사가 나뉠 수 있음을 설명합니다. 그러나 Backpack의 해당 RFQ가 Atomic Vaults에 전달됐는지, 그곳에서 거절됐는지, Backpack이 먼저 검사했는지는 확인되지 않습니다. 일반 연동 문서를 Backpack의 실제 적용 설정으로 간주할 수 없습니다.

## 4. API 설명과 실험 기록의 대조

[Backpack API 문서](https://docs.backpack.exchange/)의 RFQ 설명은 제출과 수락을 구분합니다. 지연 결제 흐름의 자산 잠금은 견적 수락 후 설명됩니다. **수락 후 자산 잠금은 수락 전 잔고 검사의 이유를 설명하는 근거가 아닙니다.** API의 `INSUFFICIENT_FUNDS` 오류 열거에도 이 검사 시점의 이유는 없습니다.

[실험 코드](../src/backpack/quote.js)는 `executionMode: 'AwaitAccept'`로 매도 요청을 보내며 견적을 수락하지 않습니다. [최초 기록](../data/quotes.compare.jsonl)의 오류는 서버가 `POST /api/v1/rfq`에 반환한 HTTP 400입니다. 따라서 자동 매도 실행에서 발생한 오류를 가격 조회 실패로 오인한 것은 아닙니다.

[후속 관측](rfq-paired-observation-2026-09-11.md)에서는 0.01주 잔고를 마련하고 같은 수량의 견적을 10회 받은 뒤 취소했습니다. 최초 약 1주 요청과는 수량·시간대가 달라, 검사 규칙이나 경계값을 분리해 검증한 실험은 아닙니다. 코드의 잔고 예약 관련 주석도 서비스 정책을 입증하는 자료가 아닙니다.

## 아티클에 반영할 방향

RFQ 실패를 조사 계기로 쓰는 것은 가능합니다. 다만 “실패 원인을 권리 구조에서 찾아냈다”는 연결은 피해야 합니다. 다음 정도로 연결하면 관측과 조사 결과의 관계가 드러납니다.

> 저희가 사용한 매도 견적 요청은 실제로 팔겠다고 수락하기 전부터 잔고 부족으로 거절됐습니다. 약관에는 계정 자산이 부족하면 거래를 진행하지 않을 수 있다는 조건이 있지만, 견적 단계부터 검사하는 이유는 공개 자료에서 확인하지 못했습니다. 그래서 먼저 이 서비스에서 ‘팔 수 있는 잔고’가 무엇인지 살펴봤습니다. Backpack의 설명에서 그것은 지갑에 남아 있는 토큰과 구분됩니다. 지원 토큰을 입금하고 전환한 뒤, 서비스 계정에 주식 보유분으로 기록되는 것입니다.

정확한 정책 이유를 확정하려면 Backpack에 다음을 확인해야 합니다. 아래는 문의 초안이며 발송하지 않았습니다.

1. 주식 `Ask` RFQ를 `AwaitAccept`로 제출할 때 사용 가능 주식 잔고를 검사하나요? 그 기준은 무엇인가요?
2. 이 검사는 Backpack의 공통 RFQ 정책인가요, 주식 상품 정책인가요, 연결 증권사의 요구인가요?
3. 제출 시 잔고를 검사하는 것과 수락 후 자산을 잠그는 것은 어떻게 구분되나요?
4. 잔고 없이 수량별 참고 매도 견적을 조회할 수 있는 별도 경로가 있나요?
